Mercy SF Web Dashboard

A browser dashboard built around the Mercy SF Shakes & Fidget CLI — overview, control, live data, and analytics for all accounts, without the terminal menu. Runs on your own server, fully mobile-friendly.

Node.js + Express No build step AES-256 encrypted credentials AGPLv3
Go to repository View installation ☕ Support Mercy SF
⚠️ Experimental, use at your own risk. This dashboard is under active development and may contain bugs. Automated play (botting) generally violates Shakes & Fidget's terms of service — there is an inherent risk of account suspension, regardless of whether the automation runs through this dashboard or directly via the CLI.

01What is this?

Everything runs on top of the official Mercy SF CLI — nothing about the bot itself is changed, this just builds a complete web interface around it. It also pulls live data (equipment, guild, tavern, mail) directly from the game server via sf-api by the-marenga.

03Features

An overview of everything the dashboard brings along.

🖧

Nodes (multi-server)

Accounts don't have to run on the server the dashboard itself is installed on. Additional servers get a lightweight node agent, connected via IP + a time-limited pairing code — control, console, stats, and CLI/node-agent updates all run transparently through the respective node.

▦

Overview

Collapsible cards (state is remembered): accounts table, character stats, equipment, tavern, guild, mail, battle history, activity log.

🗂

Account management

Log in once — every character on a login is found automatically across all servers. Passwords are stored AES-256-encrypted on disk. Start/stop/pause/"claim" per account, bulk actions per login.

⚔

Battle history

Real fights recorded locally by the CLI process — opponent, arena/dungeon/scrapbook, win/loss, XP/gold/honor — via the non-interactive CLI command --history.

⌨

Web terminal

Its own console session per account in the browser (xterm.js), including automated login click-through all the way to the running bot.

🛡

Live game data

Equipment, guild, tavern, and mail directly from the game server (read-only, local Rust service). Polling interval freely configurable (10 min / 1×/hour / 1×/day).

📈

Analytics & earnings

SQLite-backed breakdown of XP/gold/honor per day, detected fight windows, time-series charts for level, experience, gold, mushrooms, honor, rank.

⚙

Settings & templates

Every bot config toggle right in the browser — reading and the officially supported auto_* toggles go through the non-interactive CLI command --config. Save config as a template and apply it to other characters, or import from a Windows-app backup.

🔔

Notifications

Automatically detects errors/warnings from the log output — a bell with a badge and toast popups.

🕶

Anonymous mode

Pixelates character names, e.g. for screenshots or streaming — one click, effective immediately.

🔁

Auto-restart

Characters that were active before a restart/update start back up automatically afterward — staggered, so they don't all log in at once.

📱

Mobile-friendly

Fully responsive layout — navigation as a menu, tables and console adapt to screen width.

⟳

Auto update check

CLI and dashboard permanently show their update status; one click installs automatically (git pull + rebuild or binary swap).

🔐

Access protection

One dashboard account (single admin) with a setup wizard, 12-word recovery phrase, and password change right in the interface.

04Installation

On a fresh Debian/Ubuntu server, as root.

curl -fsSL https://raw.githubusercontent.com/dandulox/MercySF_Dashboard/main/install.sh | bash

  • Dependencies & services

    The script installs Node.js, Rust/Cargo for the sf-api bridge, build tools for native modules, and the Mercy SF CLI, sets up a self-signed TLS certificate, and starts the dashboard and sf-api bridge as systemd services.

  • First visit

    The dashboard is then reachable at https://<server-ip>:8080 — a setup page walks you through creating the single dashboard account.

  • Updates

    Running the script again only updates code and dependencies — existing account data, certificates, and the installed CLI version are left untouched.

  • Multiple servers (nodes)

    Each additional server only needs a lightweight node agent instead of the full dashboard — installable with the same script and the --node flag. At the end it shows the IP and a pairing code valid for 15 minutes, which you enter in the dashboard under "Nodes".

    curl -fsSL https://raw.githubusercontent.com/dandulox/MercySF_Dashboard/main/install.sh | bash -s -- --node

Uninstallation

curl -fsSL https://raw.githubusercontent.com/dandulox/MercySF_Dashboard/main/install.sh | bash -s -- --uninstall

Removes everything: both systemd services, the entire /opt/mercy folder including dashboard code, certificates, the CLI binary, saved bot credentials, the dashboard account, and the earnings-statistics database. No intermediate step, no confirmation prompt.

05Known limitations

Since version 2.13.0, the CLI offers a documented, non-interactive JSON mode, which the dashboard uses for settings, battle history, and "claim". The actual bot start/login flow in the web terminal, however, still runs through the classic interactive text menu — so automation there still relies on pattern-matching the terminal output. If the wording of a CLI menu changes there, the automation can break until the code is adjusted.

  • No native pause command — "Pause" instead turns off all active auto_* config toggles.
  • Only ~20 auto_* toggles are officially changeable through the CLI itself (--config --set) — all other settings fields are still written directly to the config file by the dashboard.
  • No official version API for the CLI — the update check compares MD5 hashes against the public download file.
  • A dashboard self-update briefly interrupts the connection while both systemd services restart.
  • sf-api doesn't provide readable item names (only numeric IDs) — the equipment display shows slot, type, attributes, and quality, not display names.
  • Daily gold earnings are a net change per time window (can include expenses) — XP and honor are exact.
  • No rate limiting on login/password-reset attempts — mainly relevant if the dashboard is ever exposed beyond its own LAN.
  • The activity log on the overview page stays empty for node accounts, since their PTY output doesn't flow through the dashboard's local log buffer — analytics, earnings, and node status do work for node accounts, though.
  • A node agent only ever accepts exactly one paired dashboard at a time — re-pairing silently disconnects a previously connected dashboard.

07Tech stack

Node.js + Express in the backend, vanilla JS with ES modules in the frontend — deliberately without a build step. The sf-api integration is a separate, stateless Rust service that listens on 127.0.0.1 only.

Node.js + Express Vanilla JS (ES modules) node-pty + xterm.js Chart.js WebSocket (ws) better-sqlite3 Rust + axum + sf-api AES-256-GCM node-agent (multi-server)
