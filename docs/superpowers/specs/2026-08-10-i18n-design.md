# English Translation (DE/EN i18n) — Design

## Goal

Add a DE/EN language switcher to the MercySF Dashboard. All user-facing text in the
authenticated app (`index.html` + `public/pages/*.js`) and the pre-auth screens
(`login.html`, `setup.html`) becomes translatable. German remains the source of
truth and the fallback language.

## Non-goals

- No third language support beyond DE/EN (structure allows adding more later, but
  only two dictionaries are written now).
- No pluralization/ICU message format — the app's strings don't need it today.
- No test suite — this project has none; verification is manual (see below).

## Architecture

### Dictionaries

- `public/lib/i18n/de.js` and `public/lib/i18n/en.js`.
- Each defines a flat, dot-namespaced key → string map on a shared global:

  ```js
  window.MERCY_I18N = window.MERCY_I18N || {};
  window.MERCY_I18N.de = {
    'nav.overview': 'Übersicht',
    'login.title': 'Anmelden',
    // ...
  };
  ```

- Keys are namespaced by page/section (`nav.*`, `login.*`, `setup.*`, `settings.*`,
  `accounts.*`, `overview.*`, `analytics.*`, `nodes.*`, `console.*`, `topbar.*`,
  `sidebar.*`, common bits under `common.*`).
- `de.js` is populated by extracting the current literal German strings verbatim
  (no wording changes). `en.js` is the new translation, same keys.
- Both files are plain `<script>`-loaded globals — no bundler/build step exists in
  this project, so this matches its current vanilla-JS delivery model.

### Runtime helper — `public/lib/i18n.js`

Exposes on `window.i18n` (or ES module export, matching `router.js`'s existing
`type="module"` usage):

- `t(key, vars?)` — returns `dict[activeLang][key]`, falling back to
  `dict.de[key]`, then to the raw `key` string if still missing. Never throws.
  `vars` is a simple `{name: value}` substitution for `{{name}}` placeholders in
  strings that need interpolation (e.g. counts).
- `getLanguage()` — returns the current active language code (`'de'` | `'en'`).
- `setLanguage(lang)` — sets active language, updates `document.documentElement`'s
  `lang` attribute, re-applies static translations, persists the choice (see
  Persistence), and re-renders the current page (via the router) so `t()` calls in
  dynamic page code pick up the new language.
- `applyTranslations(root = document)` — walks `root.querySelectorAll('[data-i18n]')`
  and sets `textContent` from `t()`; walks `[data-i18n-attr]` (value format
  `"attr:key"` or `"attr1:key1,attr2:key2"`) and sets the named attributes
  (`placeholder`, `title`, `aria-label`, etc.) from `t()`.
- Initialization order for the active language on load:
  1. Authenticated app (`index.html`): fetched from the server
     (`GET /panel-settings`, see below). If the server has no `language` stored
     yet, fall back to `navigator.language` (matched against `de`/`en`, else
     `de`), and persist that as the initial choice.
  2. Pre-auth pages (`login.html`, `setup.html`): no authenticated endpoint is
     available yet, so these read/write `localStorage['mercy-lang']` only, same
     pattern already used for `mercy-theme`. On first successful login, the
     client syncs `localStorage['mercy-lang']` to the server if the server has no
     value yet (so a pre-auth choice carries into the authenticated app).

### Static HTML (`index.html`, `login.html`, `setup.html`)

- Add `data-i18n="key"` to elements whose text is translatable, keeping the
  current German text as the literal element content (so the page reads
  correctly even before JS executes / if JS fails).
- Add `data-i18n-attr="placeholder:key"` (etc.) where placeholder/title/aria-label
  text needs translation.
- `<html lang="de">` becomes dynamically updated by `setLanguage()`.

### Dynamic pages (`public/pages/*.js`)

- These build markup via JS template strings on each render (`accounts.js`,
  `analytics.js`, `analytics-compare.js`, `console.js`, `nodes.js`,
  `overview.js`, `settings.js`) and are re-invoked by `router.js` on navigation.
- Literal German strings inside these template strings are replaced with
  `${t('key')}` calls. No separate `applyTranslations()` call is needed for these
  — they translate themselves on every render, including the re-render triggered
  by `setLanguage()`.
- `router.js` itself has a small amount of user-facing text (e.g. nav labels) —
  same treatment.

### Persistence — server-side, extends existing `panelSettings` pattern

- `lib/panelSettings.js` already persists a global (non-per-account) preset to
  `data/panel-settings.json` (currently just `gamestatePollPreset`). Add a
  `language` field alongside it:
  - `getLanguage()` — returns stored value if it's `'de'` or `'en'`, else `null`
    (caller decides the browser-language fallback).
  - `setLanguage(lang)` — validates `lang` is `'de'`|`'en'`, writes it into the
    same JSON file, returns the applied value.
- `routes/panel-settings.js`:
  - `GET /panel-settings` response gains a `language` field
    (`panelSettings.getLanguage()`, may be `null`).
  - `POST /panel-settings` (existing endpoint used for `preset`) accepts an
    optional `language` field in the body alongside `preset`, applies via
    `panelSettings.setLanguage()` when present.
- No per-account/per-user storage — this app has a single shared admin login
  (`routes/auth.js`), so "server-side" persistence here means the one shared
  `data/panel-settings.json`, matching how the polling-interval preset already
  works.

### Switcher UI

- **Authenticated app** (`index.html` topbar): a small `DE`/`EN` icon-button pair
  next to the existing `theme-toggle-btn`, mirroring its visual style. Clicking
  the inactive language calls `i18n.setLanguage(...)`.
- **Pre-auth** (`login.html`, `setup.html`): same visual pair in a corner of the
  card, backed by `localStorage` as described above.

## Data flow

1. Page load → `i18n.js` resolves active language (server for `index.html`,
   `localStorage`/browser for pre-auth pages) → sets active dict.
2. `applyTranslations()` runs against the static DOM already in the HTML.
3. `router.js` renders the current page module, whose template strings call
   `t()` inline.
4. User clicks the language switcher → `setLanguage()` updates state, persists
   it, re-runs `applyTranslations()`, and re-triggers the router's current-page
   render — no full page reload.

## Error handling

- Missing translation key → fallback chain (`activeLang` → `de` → raw key),
  never throws, never blocks rendering.
- `POST /panel-settings` failing while saving language → existing toast-error
  pattern (see `overview.js`/`settings.js` for the established toast helper),
  language still switches locally for the current session even if persistence
  failed.

## Testing / verification

No automated test suite exists in this project. Verification is manual:

- Launch the dashboard (`npm start` / existing dev workflow).
- Click through every page (Overview, Accounts, Analytics, Analytics-Compare,
  Nodes, Settings, Console) in both languages, confirming no missing keys
  (visible as raw `key.strings`) and no leftover German text.
- Confirm `login.html` and `setup.html` switch and persist via `localStorage`.
- Confirm logging in after a pre-auth language choice carries that choice into
  the authenticated app, and that reloading the authenticated app preserves the
  language via `data/panel-settings.json`.

## Scope / rollout

Implementation proceeds page-by-page (extract strings → add DE/EN keys → replace
with `t()`/`data-i18n`), rather than as a single sweeping diff, given the size of
`public/pages/*.js` (~3700 lines across the app). Suggested order: shared
infra (`i18n.js`, dictionaries, `panelSettings` change) → `index.html` shell →
`login.html`/`setup.html` → pages in rough size order (console, analytics,
analytics-compare, nodes, settings, accounts, overview).
